# 采购归档证据图工作台（Procurement Archive Evidence Workbench）

完全在**浏览器本地**运行的政府采购离线归档证据图工作台。技术栈：**React 18 + TypeScript + Vite + IndexedDB + WebWorker**，无后端、无任何网络请求，所有数据驻留浏览器。

## 1. 它解决什么问题

政策研究咨询团队从多省政府采购网页、打印件、复制文本与附件摘要中重建**可复算的项目事实集**，并回答：每个项目、标段、预算变动、公告阶段与中标结果究竟由哪一份材料支持。

- 项目编号、采购人名称、金额写法常不一致；同一事项会经历意向 → 公告 → 更正 → 延期 → 撤销 → 结果多个阶段。
- 按标题去重会把相近项目或不同标段并在一起；按最新文件覆盖旧记录会抹去预算与时限变化的依据。

本工作台把每份材料冻结为**带内容指纹的快照**，把事实连接到**字符级原文证据**，把文件间关系交给**带理由的候选边 + 人工裁决**，发布器只从**指定裁决水位**生成版本化项目链与统计快照，且任一发布字段均可回溯到「快照 → 提取规则 → 事实 → 裁决」。

## 2. 核心能力与硬规则

| 模块 | 能力 | 关键规则 |
| --- | --- | --- |
| 快照仓 | 文件来源、SHA-256 内容指纹、规范化指纹、导入批次、原文片段、解析版本 | 相同内容指纹只建一个快照、合并来源记录，**绝不会变成两个项目**；批次启动时冻结载荷，解析期间替换源文件不影响本批，新文件进入后续批次 |
| 结构解析器 `parser.ts` | 区分公告正文 / 附件摘要 / 站点噪声（导航、面包屑、版权、广告、打印页脚） | 纯函数，版本号 `parser-x.y.z` 随快照冻结 |
| 事实提取器 `extractor.ts` | 编号、采购人、标段、金额（万元自动换算为元）、日期、阶段、结果，以及拆分采购需求特征（标题/品类/交付地点/数量单位/采购人层级/地区/采购方式/计划编号/联合采购） | 每条事实携带 `[start,end)` 字符证据与规则 id（`R-CODE-01` 起共 24 条规则）；阶段按固定优先级选择，不依赖存储顺序 |
| 关系求值器 `evaluator.ts` | 同件副本 / 阶段演进 / 疑似更正 / 疑似重启 / 互斥冲突 5 类候选边 | **同编号且标段范围互斥时只能产生 `pending` 的 conflict 边，禁止自动合并**；同件副本依据规范化指纹自动确认；相同输入确定性生成相同边 id |
| 裁决记录 `engine.ts` | 审核结论、适用证据、审核员；重新裁决撤回旧关系并留痕 | 撤回记录持久化于 `withdrawn` 仓储，含新旧裁决 id |
| 增量规划器 `incremental.ts` | 并查集维护文档关系图连通分量与依赖指纹 | 仅重算受新快照/新裁决影响的分量；干净分量发布结果逐字段断言，依赖追踪失败时**拒绝发布过时项目链** |
| 项目发布器 `publisher.ts` | 项目链、标段事实、预算变动轨迹（含被更正覆盖的历史值）、统计快照 | 只消费已确认边与裁决水位；conflict 边即使被确认也不合并；每个字段带 `factId + snapshotId` 溯源 |
| **疑似拆分采购分析** `splitAnalysis.ts` | 政策目录、需求特征器、候选生成器、约束求值器、案件视图 | **只输出待核候选组合，不下违法结论**；按每个项目公告日适用政策区间（不用当前门槛重判历史）；独立计划/不同主体/不可比品类被排除且留痕；代表组合按证据强度互不重叠、金额去重；链路裁决拆分后组合失效并生成新案件版本 |

两种计算模式（全量 / 增量）从**同一批快照和裁决版本**必须得到相同的已确认事实，工作台提供「双模式一致性校验」按钮可直接验证；发布版本中记录计算模式、重算/跳过的连通分量与依赖指纹。

### 2.1 疑似拆分采购组合分析（新增数据产品）

审计研究人员希望从已发布项目链中发现**可能被拆成多笔小额采购**的组合，用于安排人工核查。系统明确区分“金额相近”与“违规”：跨部门联合采购、正常分批交付与后补更正都会造成表面聚集，因此本产品只产出**待核组合与可回查证据**。

| 组件 | 文件 | 说明 |
| --- | --- | --- |
| 政策目录 | `core/policy.ts` | 保存地区、采购方式、生效期间的**金额门槛、允许合并时间窗、引用依据**；按公告日选择适用版本 |
| 需求特征器 | `core/demandFeatures.ts` | 从标段标题、品类、交付地点、数量单位、采购人层级（附地区/采购方式/公告日）形成可回查特征，每项带事实 id + 快照 id + 原文区间 + 规则 id |
| 候选生成器 | `core/splitAnalysis.ts` | 在同一适用政策区间内按采购人/品类构造项目组合，计算合计金额、时间跨度、特征重叠与不确定字段 |
| 约束求值器 | `core/splitAnalysis.ts` | 排除已有明确独立计划、不同采购主体、无法比较品类的组合；未达门槛/超窗/跨区间也记录理由而非静默丢弃 |
| 案件视图 | `pages/SplitAnalysisPage.tsx` | 待核组合、支持/反驳证据、替代分组、规则与政策版本、重叠说明、历史案件回放；可切换“召回优先 / 有限容量”呈现策略 |

**关键规则**

- **政策按公告日分段**：每个项目按自身公告日选择适用门槛与时间窗，分属不同政策区间的项目不会合并，也不能用当前门槛重判历史。
- **两种候选呈现方式**（审计团队按召回或核查容量取舍）：`recall` 保留全部相连候选（覆盖更全、同一项目出现在多组、工作量更大）；`capacity` 只呈互不重叠代表组合（队列更短、金额不重复，但边界项目留在未分组范围）。两者都只展示候选，不下定性结论。
- **重叠不重复累计**：代表组合的合计金额按“项目单元”去重；`connectedCandidateSumCny` 单独展示保留全部候选时的重复展示量，便于审计比较。
- **链路裁决更正**：若某条项目链后来被裁决拆为两个独立标段（冲突边裁决 `split`），依赖它的组合失效并生成新的案件版本，旧版本保留在版本历史与历史回放中。
- **可复算**：拆分采购分析随发布版本在同一水位生成，并纳入「双模式一致性校验」与「离线复跑」，同一水位重建结果必须一致。

## 3. 目录结构

```
src/
  core/                纯逻辑层（不依赖 React/DOM，可在 Node 与 Worker 复用）
    types.ts           领域类型
    hash.ts            SHA-256 指纹、规范化文本、确定性 id
    parser.ts          结构解析器
    extractor.ts       规则化事实提取器（24 条规则，含拆分采购需求特征）
    evaluator.ts       关系求值器
    incremental.ts     连通分量与增量计划
    publisher.ts       项目发布器（同水位生成拆分采购分析）
    policy.ts          政策目录（地区/方式/生效期门槛、时间窗、引用依据）
    demandFeatures.ts  需求特征器（可回查相似性证据）
    splitAnalysis.ts   候选生成 + 约束求值 + 案件视图数据 + 版本化
    engine.ts          流水线编排（导入/裁决/重算/一致性/复跑/政策设置）
    repository.ts      IndexedDB 仓储
    memoryRepository.ts 内存仓储（测试用）
    *.test.ts          Vitest 验收测试（37 个，含 SHA-256 标准向量、IDB 端到端与拆分采购分析）
  workers/
    pipeline.worker.ts WebWorker 流水线
    workerClient.ts    主线程 Promise RPC
  pages/ components/ state/  React 工作台界面（含「拆分采购分析」页）
sample-archive/        12 份虚构多省归档材料（见第 6.1 节）
sample-archive/split/  16 份疑似拆分采购分析样例（见第 6.2 节）
```

## 4. 本地启动

### 4.1 开发模式（Node 22）

```bash
npm install        # 内部源已配置 npmmirror
npm run dev        # http://localhost:5173
```

### 4.2 生产构建 / 本地预览

```bash
npm run build      # 类型检查 + 构建到 dist/
npm run preview    # http://localhost:4173
```

### 4.3 Docker 一键启动（交付物含 Dockerfile / Compose）

```bash
docker compose up -d --build
# 打开 http://localhost:8080
docker compose logs -f
docker compose down
```

> 说明：当前交付沙箱内未安装 Docker 守护进程，未能实际执行镜像构建；Dockerfile 采用 `node:22-alpine` 多阶段构建 + `nginx:1.27-alpine` 托管静态资源，等价的 `npm run build` 与 `vite preview` 已在本环境验证通过（见第 7 节）。

### 4.4 测试账号 / 身份

本系统为纯本地单用户工具，**没有登录体系、没有账号密码**。裁决时的「审核员」字段为自由文本，默认值 `default-reviewer`（测试中使用 `tester` / `idb-tester`）。所有数据仅存于浏览器 IndexedDB（库名 `procurement_workbench`），清除站点数据或使用流水线页「清空本地全部数据」即可重置。

拆分采购分析的**门槛切换**在「拆分采购分析」页的政策目录区块操作（默认目录 / 浙江 2024 起 100 万 / 160 万对照），点击「应用并重算」后生成新版本；历史发布版本仍保留原门槛，可在版本选择器中回放对照。

## 5. 工作台操作与验收路径

1. **快照导入**页 → 「一键载入 12 份虚构示例归档」→ 修改批次标签 → 导入。也可用「选择文件」导入自己的 `.txt`（支持多选）。
2. **计算流水线**页 → 「全量重建」：生成事实、候选边并发布 v1。
3. **快照与证据**页 → 任一快照「查看证据」：原文中黄色高亮为事实证据、灰色删除线为站点噪声；右侧事实表给出规则 id 与字符区间。
4. **关系裁决**页：
   - 查看求值理由与适用证据，可「定位原文」联动高亮；
   - 对非冲突边执行「确认关系 / 驳回关系」；对四川 `SC2024-WZ-305` 的互斥冲突边可确认或「标记拆分」——无论如何都不会自动合并；
   - 对同一条边再次裁决，可在「撤回留痕」看到旧结论撤回记录。
5. **计算流水线**页 → 再次「全量重建」或「增量重算」生成 v2；点「双模式一致性校验」与「离线复跑」，两者均应显示绿色「一致 / 复跑一致」。
6. **项目发布**页：切换历史版本，查看项目链、预算变动轨迹、标段中标人及其逐字段溯源；互斥项目保留冲突留痕并拆分为两个项目。
7. **拆分采购分析**页（新增数据产品）：
   - 通过「一键载入 16 份『疑似拆分采购』样例」+「全量重建」生成分析；
   - 查看政策目录与各项目适用区间；用「门槛切换演示」按钮切换门槛并「应用并重算」，确认新版本按新门槛、历史版本仍按旧门槛（不代表重判历史）；
   - 在「候选呈现策略」切换「召回优先 / 有限容量」并重算，观察案件队列与金额去重差异；
   - 打开任一案件：查看代表组合（去重金额）、全部相连候选（含重叠说明）、支持/反驳证据、替代分组与案件版本历史；
   - 在「关系裁决」页把绍兴 `ZJ2024-5001` 的互斥冲突边「标记拆分」，回到分析页重算：依赖它的组合失效并生成新案件版本（勾选“显示已失效案件”可在历史回放中查看）。

## 7. 已实际执行的验证

以下验证均在交付环境（Node 22.14.0）实际执行：

1. **单元/验收测试**：`npm test`（Vitest）→ **4 个测试文件、37 个用例全部通过**，覆盖：
   - 结构解析区分正文/附件/噪声；字节级重复内容合并来源、批内并发去重；解析期替换文件不影响启动快照；
   - 每条事实证据区间可在原文精确定位、万元换算为元、规则 id 可回溯；
   - 同件副本自动确认；互斥标段只产生待裁决 conflict 边；疑似更正（预算变动）与疑似重启边识别；候选边确定性；
   - 裁决前后项目链变化、conflict 确认后仍拆分两项目、重新裁决撤回留痕；发布字段全量溯源；统计快照自洽；
   - 双模式一致性、增量只重算脏分量且干净分量逐字段不变、清空派生数据后离线复跑与历史发布一致；发布版本记录计算范围与版本水位；
   - 基于 `fake-indexeddb` 的真实 IndexedDB 仓储端到端测试（含“重开应用”等价读取与清空）；
   - 纯 TS SHA-256 回退实现的 RFC 标准向量与 WebCrypto 交叉验证（保障局域网 HTTP 非安全上下文下可用）；
   - **疑似拆分采购分析**（`splitAnalysis.test.ts`，17 用例）：政策按公告日分段（同地区 2023/2024 门槛不同、跨区间项目不合并并留痕）；同类短期采购合计达到门槛才进入候选且金额来源可回查；门槛切换（提高门槛）减少候选数量并进入 below_threshold 排除记录；明确独立计划、跨部门联合采购、不同采购主体、不可比品类均被排除且理由可回查；同一项目出现在多组候选时代表组合金额按项目单元去重、`connectedCandidateSumCny` 反映重复展示量；同一金额在旧门槛达标、新门槛不达标（证明未用当前门槛重判历史）；capacity 模式下队列更短并列出未分组项目；链路被裁决拆为独立标段后组合失效并生成新案件版本（历史回放记录失效）；离线复跑与双模式一致性包含拆分采购案件。
2. **类型检查**：`npx tsc -b` 无错误（strict 模式）。

## 8. 设计说明：全量 vs 增量

- **全量模式**：在固定快照水位上重新提取全部事实、重算全部候选边与项目链。适合小批次与跨文件间接冲突排查；补进一份材料也会重扫整批。
- **增量模式**：新快照才解析/提取；关系求值只重算受影响配对；并查集连通分量配合依赖指纹（快照哈希 + 边裁决集合）标记脏分量，发布只重算脏分量，并对干净分量与上一版发布做逐字段不变量断言，失败即拒绝发布。
- 规模超过 `INCREMENTAL_THRESHOLD = 30` 个快照时，`auto` 模式自动选择增量；两种模式的等价性由「双模式一致性校验」与测试保证。

## 9. 设计说明：疑似拆分采购分析的取舍与边界

- **为什么不做自动定性**：金额相近只是“表面聚集”。系统只把在同一适用政策区间内、同一采购人、同一品类、时间窗内、合计达到门槛的项目组合标为“待人工核查”，并同时给出支持与反驳证据、替代分组与不确定字段；是否规避程序由审计员判断。
- **召回 vs 核查容量**：`recall` 保留全部相连候选，同一项目可能出现在多组候选（覆盖更全、工作量更大）；`capacity` 按证据强度选择互不重叠代表组合（队列更短、金额去重、边界项目留在未分组范围）。两种模式下代表组合的合计金额均按“项目单元”去重，`connectedCandidateSumCny` 单独给出保留全部候选时的重复展示量。
- **政策版本**：政策目录按地区、采购方式与生效期间保存门槛与时间窗；每个项目按**公告日**选择区间，跨区间项目不合并、也不用当前门槛重判历史。门槛切换只影响后续重算版本，历史发布保留。
- **链路裁决更正**：冲突边裁决 `split` 后，项目被认定为相互独立标段；依赖它的组合失效并生成新案件版本，旧版本在 `versions` 与 `history` 中保留，可回放。
- **不确定性**：缺地区/采购方式/公告日/品类/金额的项目不臆造结论，而是进入 `excluded`（附理由）或 `uncertainties`，并在特征表标记缺失字段。
